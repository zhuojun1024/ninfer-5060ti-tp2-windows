## 1. Goals and Non-Goals

### 1.1 Goals
- Support **startup-fixed concurrency C (1..8, ≤4 in the first phase)** on the `--devices a,b` TP-2 route: B decode-ready requests form one compact decode batch, and both cards run one lockstep forward within one round.
- Aggregate decode throughput approximately linear in B (provisional gate: ≥1.6× at B=2, ≥2.5× at B=4, relative to C=1 in the same configuration).
- Per-lane output, budget, stop, cancellation, and terminal-state semantics consistent with the single-GPU EngineCore contract.
- Single-request behavior (C=1) does not regress bit-for-bit / within the established tolerance against existing TP-2 measurements.

### 1.2 Non-Goals (not done in the first phase)
- Preemptive scheduling, priority/QoS, request priority inversion handling.
- Large-scale continuous batching, cross-Engine context store, generalized multi-GPU placement (still limited to two cards).
- Prefill batching: the single-GPU contract is already "at most one staged prefill at a time", so prefill continues single-lane (decode rounds are interleaved between chunks).
- Cross-session retention and stable block reuse under multi-concurrency (added in Phase 2).
- Multimodal request concurrency (Phase 1 serializes multimodal lanes).

## 3. Gain Model and Feasibility Verdict

### 3.1 Why Only True Batching Makes Sense
- batch-1 decode is **weight-stream-bandwidth bound**: the round-time floor = weight bytes per shard / 448 GB/s; the measured 38.2 ms is ≈59% of the floor (`docs/tp2-dual-5060ti.md:125-131`), and ninfer streams 10.15 GB per shard per forward.
- Time-slice round robin does not amortize the weight read ⇒ no throughput gain; true batching lets B lanes share one weight stream ⇒ aggregate ≈B×.
- Extra costs brought by batching: T=B amplification of attention/GEMM, allreduce payload ×B (hidden 5120×B×2 B, only 80 KiB even at B=8, negligible), host-side per-lane accept/fold/session/sampling.

### 3.2 Per-Layer Feasibility

| Layer | Status quo | Verdict |
|---|---|---|
| Quantized GEMM / attention / GDN / sampling | `ops::sample` natively takes `[physical_rows,B]` + `SamplingConfig[B]` (`include/ninfer/ops/sampling.h:36-48`); `propose_dflash2_batch` frames are `[...,B]` (`execution/draft.cpp:277-300`) | No change needed |
| Paged KV multi-row | `KVExecutionTablePool::row_count/acquire/publish`, `DeviceKVPagePool::reserve/materialize` (`src/core/paged_kv_cache.h:217-232/349-351`) | Primitives complete |
| GDN state multi-slot | Single-GPU path plans by `C + device_state_slots` (`program/planning/startup.cpp:109-149`) | Primitives complete |
| CUDA graph exact-B bucketing | Single-GPU path `topology_class*max_concurrency+(B-1)` (`program/graphs.cpp:328-329/365-366`) | There is a reference; the TP-2 side must be redone |
| Batch decode model execution | Single-GPU path has `target_verify_batch`/`mtp_forward_decode_batch`/`mtp_propose_batch` + `[.,.,B]` frames (`program/speculative/mtp.cpp:70-200`) | Needs new TP-2 batch variants |
| TP-2 execution composition | All single-row | Must be written anew |
| Scheduling / admission / request state machine | None | Must be written anew or the Program reworked |
| Session cache / prefix reuse | Single-lineage global state | Must become per-lane |

**Key narrowing**: the single-GPU contract "at most one staged prefill at a time" (`engine-architecture.md:360-367`) lets prefill stay single-lane; only the decode/verify/MTP/DFlash2 windows need batch variants, roughly halving the `text.cpp` change surface.

### 3.3 Memory Budget (Hard Constraint for the First Phase)

**Authoritative ledger** (`docs/tp2-dual-5060ti.md:489-521`, factory configuration of 262,144 / fp8 KV / MTP K=2; int8 KV is **48 MiB larger** under the same accounting, because of the 64-element scale group):

| Component | shard 0 | shard 1 | Concurrency increment |
|---|---:|---:|---|
| Weights + CUDA context | 11,494.6 | 11,494.6 | 0 |
| Text KV (16.125 KiB/token/shard; fp8 262144 → 4,128.0) | 4,128.0 | 4,128.0 | **0 (shared pool: Σ lane active tokens ≤ capacity)** |
| MTP layer KV (2 KiB/token, shard 0 only) | 516.2 | 0.0 | 0 |
| Linear-attention state arena (2 live + 2 reuse snapshots = 4×73.4) | 293.6 | 293.6 | **+73.4 MiB/shard/lane**; with retention off a lane occupies only 1 plane ⇒ **C≤4 fits exactly into the existing 4 planes, zero increment**; C=8 needs +293.6. **⚠ Corrected by measurement on 2026-09-30 and settled (P1.2b = direction c)**: P1.2a changing `slot_count` to `lanes` makes `state_bytes` itself ×lanes, while the arena remains `(2+kReuseSnapshotCount)×state_bytes` ⇒ the real cost is **+293.6 MiB/shard/lane** (at C=4 the state goes 293.6 → 1174.4 MiB/shard, +880.8), **not a zero increment**; budget by the measured value. The accompanying D5 is mechanically enforced by `lanes_ > 1` (see §11.1). |
| Program workspace arena (prefill chunk 1024 peak ≈140) | 192.0 | 192.0 | To be measured: the batch window T=B raises it; budget +0…+96 for now |
| MTP replay records / round anchor | 2.6 | 2.6 | Grows slightly with B (within a few MiB) |
| DFlash2 draft ring | ≈40 | 0 | Per-lane would be +40/lane (shard 0); **the implementation chose sharing ⇒ 0** |
| **Whole-card occupancy (nvidia-smi, C=1)** | **15,614** | **15,094** | 16,311 MiB/card |

**Verdict**:
- The factory 262,144 configuration leaves **697 / 1,217 MiB** at C=1; the live server on this machine on 2026-09-30 (245760 / int8 / DFlash2 K=5) measured 15,162 / 14,834 ⇒ leaving **1,149 / 1,477 MiB**.
- **A shared KV is a hard prerequisite, not an optimization**: if each lane occupied the full context, C=4 @131072 would need 4×2,064 = 8,256 MiB/shard, directly infeasible.
- C=4 + retention off + shared KV/ring: increment ≈0 (state reuses the existing 4 planes) ⇒ ample headroom. C=8: +293.6 (state) plus workspace/ring growth would squeeze below <150 MiB at 262,144 ⇒ **unacceptable**.
- Conclusion: the first phase is **131072 + shared KV + retention off, C≤4**; placing C>2 at 262,144 first requires freeing MTP/draft or lowering the KV dtype.

⇒ **The real boundary of semantics A**: the TP-2 concurrency capacity is **1 running + 1 queued = 2** (`{1,1}` in `src/serve/serve_options.cpp:429-434`); the 3rd concurrent request is **immediately 429'd, not queued**; `--max-pending-requests 16` has no effect on TP-2. This closes the "C=1/2/4 smoke" item at `tp2-plan.md §3`: C=4 does **not** queue, it is simply rejected.

**P0.4 Baseline reproducibility**: `temperature:0` is **not bit-for-bit reproducible** on the dflash2 route — running the same prompt 4 times in a row, the pairwise common prefix is only 15–71 characters / about 350 characters; and `cache_n` oscillates between 0/1 with cold/warm. This is consistent with `tp2-plan.md §3.3` (sparse acceptance + per-request random seed, `translate.cpp:51-57`). Therefore:
- What is frozen is a **soft baseline**: configuration + throughput profile (pure decode ≈150 tok/s; for a 96-token request the draft acceptance is 79/96; prompt 70–360 ms, with 903 ms once seen on the process's first request) + one run's text (`_temp/tp2_p0_baseline_run1.txt`, `run2.txt`).
- The hard oracle must be offline (`--greedy` or a fixed-seed C++ TP-2 suite); the HTTP end-to-end only does throughput/behavior/termination semantics A/B, and text comparison switches to an agreement-rate tolerance (see §8).

## 4. Architecture Plan

### 4.1 Selection
- **Option A (recommended for Phase 1)**: build a worker thread + lane slots + FIFO admission + round loop inside `TP2GenerationCore`, reusing the existing lockstep execution and session/checkpoint machinery (Phase 1 disables cross-session retention). Self-contained and incrementally deliverable; the cost is continuing to duplicate EngineCore's scheduling semantics (the drift risk at `tp2-plan.md §3.6-§3.7`).
- **Option B (evaluated at Phase 3)**: converge TP-2 into a dual-device execution backend of `Program`, reusing EngineCore entirely for scheduling/admission/resources/caching, directly eliminating dual-core drift. It spans all layers of `Program`/`SequencePlanner`/KV/StateImage/workspace/graph planning, so the effort is large.

### 4.2 Phase 1 Minimal Usable Form
- `max_concurrency = C`, `max_pending_requests = P` come in through the CLI into normalization (no longer forced to 1).
- KV: shared physical page pool + one execution row per lane + a per-lane reservation; `--kv-capacity` semantics take effect (total budget).
- GDN state: `slot_count = C` (one live slot per lane + one round scratch per lane); Phase 1 does not do per-lane snapshots.
- Round: `batch_capacity = C`; decode round members = all currently decode-ready lanes (compact, no padding).
- Execution: unified to eager (`EagerBucket`); no `(bucket,B)` CUDA graph for now.
- Scheduling: FIFO admission + single staged prefill + decode must not starve; no backfill protection, no preemption.
- Multimodal: serialize by taking a global vision lock.
- Output: per-lane independent `OutputSink`/budget/finish reason, published per lane after the round commits.

### 4.3 Interface Sketch (Phase 1 Target Form)
```
// Execution composition layer: add a batch window variant (the single-row version is kept for C=1 and prefill)
void forward_tp2_window_batch(TextContext& peer, tp::DevicePair& pair,
                              const std::int32_t* ids,      // [B * width] row-major
                              const std::int32_t* positions,// [B * width]
                              const Tensor& kv_table_rows,  // I32 [B]
                              const Tensor& state_src, const Tensor& state_dst, // I32 [B]
                              ops::CausalAttentionExecutionEnvelope envelope,   // widest in the batch
                              Tensor& logits_columns,      // [V, B*width]
                              Tensor* hidden_columns, DFlashFeatureSink* sink,
                              const std::int32_t* valid_columns);
```
- `RoundStateSpec.batch_capacity = C`; the ingress structures (`OrdinaryDecodeIngress`/`MtpDecodeIngress`/`DFlashDecodeIngress`) fill `text_kv_table_rows[B]`, `state_*_slots[B]`, `positions[B]` by row, following `program/decode.cpp:45/285/401/559/759`.
- `round_base` becomes **planned uniformly at startup** (on top of per-lane persistent scratch) and thus a constant; otherwise the watermark condition of `reusable_window_graph` (`tp2_generation_core.cpp:987/1103/1200`) cannot be satisfied.

## 5. Change-Point List

### A. Execution Composition Layer (`TextContext`)
- A1 Add batch variants: `forward_tp2_decode_window`/`forward_tp2_window` (`text.h:179-250`, `text.cpp:2054-2900`), accepting `[B]` positions, `kv_table_rows[B]`, state slots `[B]`, per-row envelope/valid_columns; `forward_tp2`'s logits expand from `[V,1]` to `[V,B]`. Follow `target_verify_batch` and the single-GPU ordinary decode batch.
- A2 `mtp_chain_body` (`tp2_generation_core.cpp:1212-1330`) becomes batched or loops per lane, with per-lane pinned ingress; follow `mtp_forward_decode_batch`/`mtp_propose_batch` in `program/speculative/mtp.cpp:70-200`.
- A3 DFlash2: change the batch of `plan_dflash2_round`/`dflash2_proposal_workspace_bytes` from 1 to B (`tp2_generation_core.cpp:767-774`), plus `DFlash2RoundSpec.batch_capacity` (`program/dflash_round.h:58`) and the per-lane ring/frame.
- A4 The allreduce payload widens with T×B: confirm that the clamps of `in_kernel_allreduce_bytes()` (`device_pair.h:48-52`) and `prefill_chunk_width` (`tp2_generation_core.cpp:1362`) still hold.

### B. Core and Scheduling
- B1 Replace inline execution in `wait()` with a worker + lane slots + events (`tp2_generation_core.h:353`, `.cpp:1458-1473`).
- B2 Split `execute_walk` (starting at `tp2_generation_core.cpp:2431`) into resumable stages: materialize → prefill chunk (single lane) → first sample → decode rounds (batch) → finish; hoist the decode round loop up into the core.
- B3 Make core-level global state per-lane (all fields listed at `tp2_generation_core.h:519-578`).
- B4 Cancellation: compact batch membership at round boundaries; releasing the cancelled lane's KV/state must not affect other lanes in the same batch.

### C. Resources, KV and State
- C1 `kv_table_rows = 1 -> C` (`tp2_generation_core.cpp:592`); change the startup pinning of all pages to row 0 into a shared pool + per-lane reservation/materialize (`:841-887`). Beware the per-request reserve/materialize leak family recorded at worklog:380.
- C2 GDN `slot_count = 1 -> C` (`:616`), one copy of `kRoundScratchSlot` per lane.
- C3 `RoundStateSpec.batch_capacity = 1 -> C` (`:900`); MTP KV pages likewise multi-row.
- C4 Admission/capacity: Phase 1 uses a **static or simplified partition** (a fixed page-group cap per lane) and does not port ResourceManager's backfill proof; `--kv-capacity` becomes a real total budget.

### D. CUDA Graph and Transfers
- D1 The graph key expands from visible extent to `(bucket, B)`; the three step classes' pinned ingress become `[B*width]`.
- D2 `reserve_ar_channels` count ×C (`tp2_generation_core.cpp:523`, currently 24 → about 192), and it must be computed correctly before the first `create_ar_channel` (what the P1 fix addressed was exactly hitting the ceiling).
- D3 `round_base` planned uniformly at startup (see 4.3).
- D4 Phase 1 may ship eager only (dropping the D1/D2 graph matrix), at the cost of the single-digit percentages measured on single-GPU (DFlash2 −10.2%, MTP 34.2→34.0 ms).

### E. Session and Cache
- E1 Single resident → C residents, or Phase 1 disables cross-session retention and the host checkpoint ring in multi-lane mode (`tp2_generation_core.h:215-280`).
- E2 Phase 2 rewrites catalog/eviction/recall/anchor semantics per lane, aligned with the single-GPU context cache.

### F. Multimodal
- F1 The single `vision_workspace_`/`vision_arena_` (`tp2_generation_core.cpp:706-747`) gets a global lock for serialization; Phase 2 makes it per-lane.

### G. Serving and Contracts
- G1 Open up `effective_request_capacity` to `{C, P}` (`src/serve/serve_options.cpp:429-434`), with the thread pool and request-lifetime capacity sharing one source.
- G2 Documentation: `docs/serving.md:68-69`, `docs/tp2-dual-5060ti.md:1-5/487`, `model-cards/Qwen3.8-27B-nvfp4-NInfer/README.md:219`, the product execution model section in `AGENTS.md`.

### H. Tests
- H1 All existing TP-2 tests are single-request: `tests/models/qwen3_5/test_tp2_{forward,sessions,dflash_append,dflash_solo,load}.cpp` (`test_tp2_sessions.cpp:144` and `test_tp2_dflash_solo.cpp:62` are the only two cases that set `device_b`, and both write `max_concurrency = 1`).
- H2 **Landed (2026-10-02)**: `tests/models/qwen3_5/test_tp2_lanes.cpp` (`ninfer_qwen3_5_tp2_lanes_test`) covers, through the public `Engine::submit` + `--max-concurrency 4`, the scheduling paths that previously had zero automated coverage — per-lane isolation of four lanes in the same batch (4 different prompts each running their budget to completion; the same prompt ×4 with prefix reuse disabled is token-for-token identical), over-quota requests reinserted at the head of the queue and reordered (6×600 tokens contending for a 32-page pool), queue expiry (`RequestError(QueueTimeout)`) and queued cancellation (`FinishReason::Cancelled`, zero tokens), dynamic admission into a batch (P2.2, a short request taking less than half the time of a long one), and destroying the engine with requests in flight (the driver thread stops and joins without hanging). The end-to-end 503 for `--pending-timeout-ms`/cancellation still follows the on-machine probe in §12.12.
- H3 The **byte-for-byte** criterion for pairwise oracles within a batch does not apply to the batch route (a batch shares one attention envelope sized by the longest lane, and ulp drift can flip near-tie tokens), so H2 switches to "same-prompt in-batch agreement" and near-tie criteria; the byte-for-byte oracle is used only for the single-lane route (§12.6). Concurrency tiers for `tools/bench/ttft` are recorded in §3.4 and §12.5.

## 8. Verification Plan
- **Numerical oracle**: compare every lane in the batch against the same lane run solo; use bit-exact for exact outputs, and the existing tolerance for probability paths (temperature 0 does not guarantee a bit-exact argmax, `--greedy` is required, see `tp2-plan.md §3.3`).
- **Reproducibility precondition (measured in P0.4)**: the dflash2 route does not reproduce bit-exactly even at `temperature:0` (same prompt, 4 runs: common prefix only 15–71/350 characters) ⇒ a hard oracle must be run offline under `--greedy` / a fixed seed; HTTP A/B uses prefix-agreement rate / token-agreement rate tolerance, or the entire A/B runs against a `--greedy` server.
- **Behavior**: round membership varies with B, cancellation, batch failure, terminal state and finish reason, streaming chunk order.
- **Performance**: `tools/bench/ttft` concurrency tiers + `tools/win_port/bench_serve.ps1`; report aggregate tok/s, round time, per-draft acceptance rate, and the ratio to C=1.
- **Memory**: per-shard `[mem]` ledger + `nvidia-smi` measured free; combinations of C and context tier.
- **Regression**: the TP-2 suites of `tools/win_port/test.ps1` (`ninfer_qwen3_5_tp2_*`, `ninfer_tp_device_pair_test`, `ninfer_engine_options_test`, `ninfer_serve_options_test`) all green.
- **The disabled items and contracts must be verified explicitly**: Phase 1's two "disabled items" have both been lifted in Phase 2 — P2.3 made cross-session retention per-lane (single-lane behavior changes not at all, see §12.6/§12.8), P2.4 lets multimodal requests into the batch (media builds one Vision session per lane inside the batch, see §12.9). Verification therefore becomes: ① a mixed multimodal + text batch is measured to actually batch and answer correctly; ② media identity participates in the prefix-reuse decision, so different images no longer reuse each other's KV (`MediaSpan` / `media_prefix_cap`, see §12.9); ③ the single-lane route does not regress byte-wise (`tp2_sessions` plain character-for-character identical to HEAD).

**state arena multiplier (measured discovery 2026-09-30; P1.2b decision = direction (c), accept the multiplier)**: `state_bytes` is the size of the **entire live pool** (`slot_count` slots), while `state_arena = (2 + kReuseSnapshotCount) * state_bytes` is four **whole-pool** copies of "2 live + 2 snapshot". Three possible directions (per Phase 1 tradeoff): (a) keep `slot_count = lanes` but change the snapshot/round-scratch planes from "whole-pool copy" to **one per lane or one shared by the whole batch**, reducing the arena from `4 x state_bytes` to about `(lanes + 2) / lanes`; (b) when retention is off, simply do not allocate the two reuse snapshot planes (the device-snapshot branch at `execute_walk:2589-2591` and the reuse scan at `:2961/:2969` do not run under D5 anyway), keeping only base + round scratch; (c) accept +880.8 MiB/shard and change the §3.3 budget table to the measured values. **Whichever is chosen, first re-confirm whether `kRoundScratchSlot = kReuseSnapshotCount = 2` still holds after going to one per lane.**

### 12.6 P2.3 design (making cross-session retention per-lane)
**Status: design settled (2026-10-01), construction pending.** This section expands the single P2.3 line of §5 E2 / §7 into a staged, constructible plan; the measured scale is **far larger** than the original one-line estimate (the original estimate implicitly assumed "add a lane parameter to the existing calls", whereas the reality is building a retention system from scratch inside the batch path).

#### Current-state measurement (why it is not just adding a lane parameter)
- All 15 retention members are referenced only inside the single-lane `execute_walk` (`src/runtime/engine/tp2_generation_core.cpp:4360-5913`): `host_checkpoint_*` 31 sites, `reuse_source_` 7, `cached_prompt_tokens_` 7, `anchor_session_` 6, `sessions_` 6, `active_session_` 5, `cached_boundaries_` 5, `cached_state_valid_` 3, `block_anchor_*` 2, `live_state_valid_` 1.
- The two batch executors `execute_plain_batch` (`tp2_generation_core.cpp:2166`) and `execute_spec_batch` (`:2558`) reference these members **0** times (the only exceptions are the comment about pulling the catalog at the tail of `execute_spec_batch` and 1 site of `dflash_context_frontier_`) ⇒ the multi-lane route has **no** retention code, and P2.3 builds it new inside the batch path.
- All 12 `session_*` functions presuppose "the whole pool = one device lineage": `session_drop` (`:3462`) maintains only a single `active_session_`; `session_evict_one` (`:3506`) relies on `device_resident` to skip resident entries (implicitly "at most one resident"); `session_recall` (`:3954`) treats `active_session_`/`cached_state_valid_`/`shard_a_.host_checkpoints` as global; there are also `session_store_active` (`:3718`), `session_restore` (`:3828`), `session_capture_shared_state` (`:3894`), `session_publish` (`:4163`).
- Ring and mirror transfers copy the whole pool raw: `build_shard` (`:790`) `checkpoint.buffer = PinnedHostBuffer(shard.state_backing.bytes)` (including all lanes); `session_store_active:3742`, `session_restore:3851`, `session_capture_shared_state:3923` are all `cudaMemcpyAsync` of `state_backing.bytes`. `src/models/qwen3_5/program/dflash_round.cpp:282-309`'s `copy_context_*` hardcodes `ring_->slot_view(0)`.

#### Memory budget (determines the mirror layout)
- Current state, lanes=1: `slots = host_state_slots(32) + divergence + block = 34`, each slot holding the whole pool at 73.4 MiB ⇒ 2495.6 MiB/shard (about 5 GiB pinned across two cards).
- Opening D5 directly without changing the layout: at lanes=4, `34 × 293.6 = 9.98 GiB/shard` (about 20 GiB pinned) ⇒ unacceptable.
- **Decision (construction version, correcting the first draft of this subsection): mirrors are stored per lane, and the ring is partitioned per lane.** The first draft said "each slot stores `lanes_` images" ⇒ `slots × state_bytes` = 9.98 GiB/shard, which contradicts the acceptance requirement that "lanes=4 and lanes=1 are of the same order of magnitude". Construction adopts: the total slot count `total = host_state_slots + divergence + block` (= 34) is divided evenly across lanes, each lane getting `host_checkpoint_slots_per_lane_ = max(1, total / lanes_)` slots (lanes=1 → 34, lanes=2 → 17, lanes=4 → 8), and **each slot stores only one compact single-lane image** (`image_bytes = layers*(conv_layer_bytes + recurrent_layer_bytes)` ≈ 73.4 MiB); a lane's slot interval is `[lane*slots_per_lane, (lane+1)*slots_per_lane)`. Total pinned = `lanes_ * slots_per_lane * image_bytes`: lanes=1/2 → 2495.6 MiB/shard, lanes=4 → 2348.8 MiB/shard (same order of magnitude, satisfying acceptance).
- Each lane's sub-layout has the same shape as the lanes=1 whole ring: `fixed = divergence(1) + block(1)`; `tail = max(1, min(kReuseTailCheckpointCount, (per_lane - fixed)/2))`; `grid = per_lane - fixed - tail`; `stride = max(kReuseCheckpointStride, round_up(ceil(max_context/grid), 128))`. ### 12.8 Stage 2c snapshot-direction bug (`copy_lane_state` D2D writes the wrong way) and the fix for `a recalled conversation` (2026-10-01)
**Nature: a regression introduced by P2.3 Stage 2c.** (This section overturns the diagnosis in the "Remaining failure" subsection of §12.7: that failure was not a Round 19-class chunk-width drift but GDN state pollution caused by a snapshot direction written backwards.)

#### Symptom
- The plain gate (single lane) fails deterministically on `a recalled conversation`: `FAIL (plain): a recalled conversation diverged from the oracle on its first sample: got [220 220 17 15 17 18 95859 15] expected [365 10715 277 198 8442 13516 1544 36133]` (`tests/models/qwen3_5/test_tp2_sessions.cpp:483-487`).
- The HEAD baseline (pwsh-419, `git stash push -- src include tests` to switch to d1a9b57b, then a full rebuild) **passes** that case and fails only at the later `a conversation behind a shared system prompt` ⇒ this is a numerical regression introduced by TP-2.
- A temporary logits probe (pwsh-442) shows this is a near-neighbor tie: engine `a_second` `first=220`, `220=5.78125 271=5.71875 365=5.71875 62=5.65625 … gap=0.06250`; the control with the same geometry (the `opening` of engine and oracle respectively, `prompt=64 reuse=0`) is **bit-identical** ⇒ the forward pass itself has no structural difference; the difference comes from two floating-point lineages.

#### Root cause (reading the code line by line)
- The three branches of `copy_lane_state(geometry, device_base, lane, other, kind, stream)` (`src/runtime/engine/tp2_generation_core.cpp:3857-3894`) disagree on the semantics of the first device pointer: D2H/H2D treat `device_base` as the **whole pool** (the source for D2H, the destination for H2D), whereas the D2D branch `cudaMemcpy2DAsync(device_conv /*=the device_base side*/, conv_pitch, source /*=other*/, conv_pitch, …)` treats `device_base` as the **destination** and `other` as the source.
- Both "snapshot" call sites pass arguments by the convention "pool is the source, plane is the destination": `:5391-5396 snapshot_lane_state` and `:2361-2366 publish_lane_prefill` both pass `(shard.state_backing.data, lane, shard.state_snapshots[slot].data, D2D)`. Under the D2D branch's actual semantics they perform the **reverse** operation — reading the plane back into the live pool.
- Consequently `state_snapshots[0]`/`[1]` are **never written forward**: `:774-779` only does `cudaMemset(shard.state_backing.data, 0, state_bytes)`, and the plane is the arena's raw device memory. Every prefix snapshot **overwrites the live pool's GDN state** with this raw memory, and the decode loop, the published session state, and the host checkpoints that follow are all built on the corrupted state.
- Why the existing got-vs-oracle checks kept passing: engine and oracle run the same code, so the corruption is **symmetric**; and the first sample happens before the first overwrite (a probe inserted after the first sample is still bit-identical).
- The two genuine *restore* call sites (`restore_lane_gdn :2276-2279`, `begin_gdn_state :5220-5222`, both `DeviceSnapshot`) are **exactly correct** under the old D2D semantics, which is also why the bug was masked for so long.
- Incidental correction (**already corrected in §12.11**): the original judgment here that "`plan_linear_attention_state_pool` (`src/core/linear_attention_state.cpp:75-112`) places the slot in the **innermost dimension** (`{conv_channels, conv_width, slot_count}` / `{key_head_dim, value_head_dim, value_heads, slot_count}`), so `conv_layer_pitch_bytes` (the true inter-layer stride) ≠ `conv_bytes` (one layer, one slot), and lanes>1 will step across slots" was a **false report** — it read the NInfer layout in row-major order (last dimension contiguous), whereas NInfer's `Tensor` is **dim 0 varying fastest** (`src/core/tensor.cpp:50-57 set_contiguous_strides`: `nb[0]=elem`, `nb[i]=nb[i-1]*ne[i-1]`), so the slot is precisely the slowest-varying/outermost dimension and `conv_layer_pitch_bytes` reflects only the arena's inter-layer padding. The conclusion, evidence, and the real defect found and fixed in the same round are in §12.11.

#### Fix (`src/runtime/engine/tp2_generation_core.cpp`, 4 edits)
- The plane writes in `snapshot_lane_state` and `publish_lane_prefill` are changed to "plane first, pool second": `copy_lane_state(geometry, plane /*device_base*/, lane, pool /*other*/, cudaMemcpyDeviceToDevice, stream)`.
- The header comment of `copy_lane_state` and the D2D branch comment are rewritten to state explicitly that "D2D writes into the first device pointer; restore passes pool first, snapshot passes plane first".

### 12.11 Verification of the leftover item "`copy_lane_state` steps across slots" and the fix for the host checkpoint target-state image overrun (2026-10-01)

#### Conclusion one: the original leftover item was a false positive (the NInfer layout is dim 0 fastest)
- NInfer's `Tensor` is **dim 0 fastest-varying**: `src/core/tensor.cpp:50-57 set_contiguous_strides` sets `stride = dtype_size; nb[0] = stride; for (i=1..3) { stride *= ne[i-1]; nb[i] = stride; }`; `slice(dim,start,len)` (`src/core/tensor.cpp:112-125`) only changes `ne[dim]` and adds `start*nb[dim]` to the pointer.
- Therefore the memory layout of `conv_shape {conv_channels, conv_width, slot_count}` is `[slot][conv_width][conv_channels]`: slot is the outermost (slowest-varying) dimension, each slot is a contiguous `conv_bytes = conv_channels*conv_width*elem` block located at in-layer offset `slot*conv_bytes`; `recurrent_shape {key_head_dim, value_head_dim, value_heads, slot_count}` is the same (`slice(3,slot,1)` ⇒ `slot*recurrent_bytes`).
- Direct evidence: `src/core/linear_attention_state.cpp:199-209 conv_slot/recurrent_slot` do `slice(2/3, slot, 1).view({...})`. `Tensor::view()` (`src/core/tensor.cpp:99-108`) throws `std::invalid_argument("view requires a contiguous tensor")` when non-contiguous, and it has never thrown ⇒ that slice is contiguous. Also `:44-71 layer_stride_bytes` verifies that the inter-layer pitch is constant (`current - previous == stride`, otherwise it throws `"... layer stride is not constant"`), and `:162-176 slot_view` uses this to produce `conv_layer_pitch_bytes` (the real inter-layer stride, including arena padding) and `conv_layer_bytes` (one layer, one slot).
- Corroborating evidence: the same "slot is a contiguous block within a layer" contract is already covered by functional tests of the 4-slot pool — `src/models/qwen3_5/state/state_image.cpp:381-458 copy_to_host/copy_from_host` copies whole blocks per layer with `cudaMemcpyAsync(dst, conv_slot(layer,source).data, conv.bytes(), ...)`; `tests/models/qwen3_5/test_state_image.cpp:132-170 test_host_roundtrip` (`slot_count == 4`, each (layer,slot) filled with distinct bytes, every slot checked after the round trip) and `:201-211` (source-isolation checks for `copy_slot(0,2)`/`zero_slot(1)`) all pass.
- ⇒ `src/runtime/engine/tp2_generation_core.cpp:4028-4067 copy_lane_state` (`device_conv = base + conv_base + lane*conv_bytes`; the D2D sides use the same layout for the whole pool, D2H/H2D use `conv_pitch`/`conv_bytes` for 2D striding) together with `:4069-4081 zero_lane_state` are **both correct** in offset and striding. §12.8 `:612` and `:627` have been corrected in place.

#### Conclusion two: the real defect in the same area — the host checkpoint's target-state image is addressed as a whole pool
- Layout fact: `shard.host_checkpoints[index].buffer` is `PinnedHostBuffer(shard.lane_state_geometry.image_bytes, true)` (`:795-796`), i.e. **one slot holds only one compact single-lane image**; `PinnedHostBuffer` allocates exactly (`src/core/arena.cu:251-264 cudaHostAlloc`, no extra expansion). The lane is expressed by the **slot index** — `:789 slots = lanes_ * host_checkpoint_slots_per_lane_`, `:5089 begin += lane * host_checkpoint_slots_per_lane_`, `:5095 host_checkpoints[begin + index]`. This matches the construction-version decision of §12.6 `:526`/`:537` (one image per slot; the "`lanes_` images per slot" option was rejected).
- Yet three copies added `lane * image_bytes` on top of the buffer again: the `HostCheckpoint` branch of `restore_lane_gdn` (formerly `:2339-2345`), `snapshot_host_checkpoint` (formerly `:5074-5078`), and `begin_gdn_state` inlined in `execute_walk` (formerly `:5399-5404`). For lane=0 the offset is 0 so it is correct; for lane≥1 the reads and writes landed in arbitrary memory roughly 73.4 MiB past the end of the pinned allocation ⇒ UB / heap corruption.
- Why it stayed hidden for so long: the write site and the read site used the **same** out-of-bounds offset, so the checkpoint round trip was self-consistent; and lane 1's host restore path really was exercised (`_temp/p23_fix_stage2b_probes.log:106` plain-pair-ring `lane=1 prompt=2890 cached=2805 shared=2783 replay_split=2783 adopted=0 prefill_end=2805 host=5/34 stride=16384 -> reuse=2560 slot=29 src=host`, slot=29 belongs to lane 1's `[17,34)`), with a coherent answer. In contrast, `store_dflash_image` (`:1908-1911`) has an explicit guardrail `if (image.size() < (size_t)(lane+1)*lane_bytes) throw std::logic_error("draft context host image is smaller than the lane's draft ring")`; the target-state path lacked the equivalent guardrail, which is how it slipped through.

#### Newly found and fixed: the peer arena leak in `TextContext::proposal_argmax` (P0.3)
- Symptom: `--spec mtp --max-concurrency 4` warmup startup reports `TP-2 batched verify CUDA Graph replay found a different workspace layout` (`tp2_generation_core.cpp:1551-1553`); `--max-concurrency 1` is fine and DFlash2 multi-lane is fine.
- Root cause: `proposal_argmax` at `src/models/qwen3_5/execution/text.cpp:822` takes a scope only for the local arena (`:823`), while the branch that splits the proposal head allocates on the **peer's arena** (`:867`/`:876`/`:878` plus the `project` scratch at `:877`) and the peer side has no scope ⇒ each call raises the peer's bump pointer by about 403,456 B that is never reclaimed. The multi-lane route runs `max_extent` MTP chain steps per round, and `max_extent` varies with the round budget (2 on the warmup capture round, 0 on the replay round) ⇒ the `arena_begin[1]` captured by the verify graph cannot be reproduced.
- Attribution: pre-existing defect (the last change to `text.cpp` is the committed `6a17bb2c`); the other peer allocation sites in the same file (`:494`/`:932`/`:1050`/`:2137`/`:2814`) all have `auto peer_scope = peer.work_.scope();`, only `:858` was missing it.
- Fix: added `auto peer_scope = peer.work_.scope();` after `:858` (with a comment, +5 lines).
- This is the same class as P2.2c recorded at `:500` of this document (allocations inside the chain step make the verify call site's `used()` drift); P2.2c only handled the local side (hoisting `positions` out of the loop) and the peer side was missed.

### 12.13 The 9 fixes of the second read-only review and the multi-lane scheduling tests (2026-10-02)

A second read-only pass over the TP-2 multi-concurrency work tree after P1–P3 yielded 9 findings, no P0/P1; the 15 core invariants (driver publish protocol, `execution_mutex_`→`lane_queue_mutex_` lock order, no duplicate publish, no UAF, KV all-or-nothing, KV arithmetic, no head-of-line starvation, deadline ahead of cancellation, destruction safety, per-lane isolation, GDN slot binding, serving capacity, the source of 413, shard 1's MTP slab empty, host checkpoint validity) were re-checked one by one and still hold. #### Fixes
- **#5** (`src/runtime/engine/model_instance.cpp:106-116`): when the converged value differs from the requested value, print to stderr `[tp2] --max-concurrency %u exceeds the %u lanes the %s route batches; running %u lanes (--max-pending-requests is unchanged)` (the backend name comes from `product::speculative_backend_name`).
